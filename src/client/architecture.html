System design

Two ways to interpret a live call, timed on one clock

Voice-to-voice: the browser talks straight to OpenAI gpt-realtime over WebRTC, and one model hears, translates and speaks. Cascade: the browser streams audio to our Node server, which runs speech-to-text → translation → text-to-speech as three swappable stages and streams the audio back. Both modes sit behind one UI and one Transport interface, get the same speech, and are stamped on the browser's clock, so we can compare latency, quality, cost, and how much of each we can see and control.

  • Speech end → first audio, p50 818 ms vs 1,395 ms voice-to-voice (n = 7) vs cascade (n = 36)
  • Cost per minute ~$0.17 vs ~$0.04 voice-to-voice grows with call length
  • Timing points you can see 3 vs 7 timing points the UI shows · voice-to-voice is a sealed box

01

System context & containers

Voice-to-voice audio never touches our server; the cascade's audio never touches OpenAI Realtime.

02

Cascade pipeline

Three stages behind typed contracts (src/shared/contracts.ts). A new vendor is one adapter file plus one registry line.

1 STT

SttProvider.open(opts) → SttStream
Receives
push(pcm) PCM16 mono 16 kHz frames · languages (the pair)
Produces
onPartial({text, lang}) · onFinal({segmentId, text, lang, endMs}), where endMs is the true end of speech
Typed errors
onError(ProviderError): disconnected · failed · rate_limited (OpenAI); a blank final is the empty turn state, not an error
Cancel
close()

2 Translate

Translator.translate(req, signal) → AsyncIterable<string>
Receives
{turnId, text, from, to, context}, context = the last 5 turns
Produces
Streamed target-text deltas; the pipeline cuts them into settled segments
Typed errors
rate_limited (one retry if nothing streamed yet) · timeout (4 s idle) · disconnected · failed · empty
Cancel
AbortSignal

3 TTS

Tts.speak(req, signal) → AsyncIterable<Uint8Array>
Receives
{turnId, segmentIdx, text, lang}, one settled segment at a time
Produces
PCM16 24 kHz chunks, sent to the browser prefixed with the turn's seq
Typed errors
rate_limited · timeout (5 s idle) · failed · empty
Cancel
AbortSignal
03

Turn state machine

Every turn is one record (TurnState) shared by both modes for display. The cascade drives each transition; voice-to-voice maps its events onto the same states.

04

What each mode can measure

Every point is stamped in browser time; server stamps are converted with a clock offset measured by ping (INV-1). The clock starts at the true end of speech, not at a vendor's notice (D10).

05

Trust boundaries

What crosses each line, and what never does.

  • Server ↔ vendors

    Keys stay on the server

    Vendor keys are read from .env by the Node process only. The browser learns vendor names from /api/config, never keys. No audio or transcript is written to disk unless an evaluation run asks.

  • Browser ↔ OpenAI

    A short-lived client secret

    For voice-to-voice the server mints a client secret that expires after 10 minutes. The browser uses it to open WebRTC to OpenAI; the long-lived key never leaves the server.

  • Public deploy

    Access code + HttpOnly cookie

    Every route and the /cascade socket need the access code (Basic auth), traded for an HttpOnly, Secure, SameSite=Strict cookie. Wrong codes are throttled at 10 a minute, the socket accepts only its own origin, and eval uploads are off.

  • Local run

    Localhost only, Host and Origin checked

    The server binds 127.0.0.1 and refuses foreign Host headers (DNS rebinding); /cascade accepts only localhost page origins. Listening publicly without a 12+ character access code is refused at start-up.

06

Scale budget

Discussion only (NFR-010): the workbench runs one session. From HLD §5.

Sessions at once First thing that breaks Response
10 Nothing: one Node process —
100 Vendor concurrency caps (STT streams, TTS sockets) and rate limits Per-vendor pools, backoff with jitter, per-stage alternates
1,000 One server's socket and memory limits; deploys drop live calls; voice-to-voice cost per minute grows with call length (context re-billing) Horizontal servers with sticky routing, graceful drain, context truncation, a retry budget to avoid retry storms
07

Key decisions

One line each; the full options, costs and reasons are in the repo.

  1. D22

    TypeScript everywhere. One language for server, browser and the shared stage contracts; a .NET server would be a port of the contracts, not a rewrite.

    ADR ↗
  2. D25

    Browser-direct WebRTC for voice-to-voice. Each mode runs the way it would in production; relaying its audio through our server would add a hop that skews its latency.

    Journal ↗
  3. D11

    Stream settled segments only. Spoken audio cannot be unsaid, so only text that has settled is translated and spoken, clause by clause.

    Journal ↗
  4. D10

    The clock starts at the true end of speech. Not at a vendor's “speech stopped” notice; the turn-detection wait is its own stage.

    Journal ↗
  5. INV-3

    Skip and mark failed turns. A stuck stage marks one turn “not interpreted” and drops its late results; later turns play on time.

    HLD ↗
  6. D19

    Barge-in cuts playback (headphones on). When the next turn's speech ends while an interpretation is still playing, the rest of it is cut, accepting that its tail is lost.

    Journal ↗
  7. Guard

    Prompt-injection guard. The utterance is fenced as data and earlier turns are background only, after a spoken “ignore your instructions” broke a cascade turn in evaluation.
